3.3.6  Smart Charging Logic Implementation
The smart charging logic constitutes the operational core of the simulation framework, orchestrating real-time decisions about when and where each electric vehicle should charge. The entire logic is encapsulated within the SmartChargingStationMonitor class, implemented in load_demand_prediction.py. This class interfaces directly with the SUMO simulation engine through the TraCI API, maintaining a persistent, second-by-second awareness of every vehicle's battery state and every station's occupancy status simultaneously across the 100-vehicle fleet.
The monitor operates under a clearly defined set of global thresholds that govern charging trigger conditions. Specifically, a State of Charge (SOC) trigger threshold of 30% is set as the lower bound (SOC_THRESHOLD = 30.0), with a SOC target of 70% upon completion of each charging session (SOC_TARGET = 70.0). The estimated charging duration at any station is calculated dynamically from the vehicle's remaining energy deficit and the station's rated power and efficiency, bounded within a minimum of 30 seconds and a maximum of 300 seconds (MIN_CHARGE_TIME = 30, MAX_CHARGE_TIME = 300). These boundaries prevent excessively short or unrealistically long charging stops within the 600-second simulation window.
Core Data Structures and State Management
To track the state of all 10 bidirectional charging stations and the 49 active EV agents simultaneously, the SmartChargingStationMonitor maintains several in-memory data structures, each updated at every simulation timestep:
station_charging_slots — A Python dictionary mapping each station identifier to a set of vehicle IDs currently occupying active charging slots. This allows O(1) lookup to determine instantaneous charging occupancy.
station_waiting_queue — A dictionary mapping each station to a collections.deque object, implementing a strict First-In, First-Out (FIFO) waiting queue for vehicles that have arrived but cannot immediately access a charging slot.
currently_charging — A reverse-lookup dictionary mapping each vehicle ID to the station where it is actively charging, enabling O(1) status checks during data collection.
currently_waiting — Similarly, a reverse-lookup dictionary mapping each vehicle ID to the station at which it is queued in a waiting slot.
vehicle_states — A nested dictionary storing per-vehicle metadata, including: the timestamp when charging began (charging_start), SOC at session start (soc_start), routed station identity (routed_to), scheduling flag (charge_scheduled), and expected slot type (expected_slot: 'charging' or 'waiting'). This state persists across timesteps to allow continuous session tracking and to prevent duplicate rerouting commands.
These data structures are initialized for all ten stations at startup and updated atomically during each call to the collect_data(t) method, which serves as the master orchestration routine invoked at every integer simulation second.
Station Configuration Dictionary
Each of the 10 stations is registered in a static CHARGING_STATIONS dictionary at the class level, directly mirroring the parameters from the Test1.chargingstations.add.xml configuration file. Each entry specifies: the charging area ID (the parking area XML ID for active charging), the waiting area ID (the separate parking area for queued vehicles), the associated lane and edge identifiers for geospatial routing calculations, the station's rated power in kilowatts (ranging from 25 kW to 50 kW), a uniform charging efficiency of 0.95, and the distinct charging slot capacity and waiting slot capacity as defined in the XML. The separation of charging and waiting areas is a fundamental architectural choice: it allows the simulation to model real-world infrastructure where vehicles physically queue in a designated zone before being promoted to an active charging berth.
Nearest-Neighbor Station Selection Algorithm
When a vehicle's SOC falls below the 30% trigger threshold and no charging session has already been scheduled for it, the system invokes the find_nearest_reachable_station(vid) method. This method implements a route-aware nearest-neighbor selection algorithm. Rather than relying on simple Euclidean distance, it queries the TraCI simulation engine using traci.simulation.findRoute(current_edge, station_edge) for every candidate station. This call returns the actual network route length along the road graph, accounting for the unidirectional nature of lanes and road topology. All reachable stations are collected as candidates, sorted in ascending order of network route length, and then evaluated sequentially according to the five-rule assignment logic described below.
Five-Rule Slot Assignment Logic
The assignment decision follows a strict priority hierarchy applied to the two nearest reachable stations. The availability check for any station is performed by the is_station_available(station_id, check_waiting) helper, which compares the current occupancy count (number of vehicles in the station_charging_slots set) against the configured charging capacity, and optionally checks the waiting queue length against the waiting capacity. The five sequential rules are:
Nearest station has a free charging slot. The vehicle is immediately routed to the nearest station and directed to its charging parking area (charging_area). This is the optimal outcome—minimum travel distance with direct energy transfer.
Nearest station charging is full; second-nearest station is evaluated. If the nearest station has no free charging slot (checking charging slots only, not waiting slots), the algorithm advances to the second-nearest reachable station.
Second-nearest station has a free charging slot. The vehicle is routed to the second-nearest station and directed to its charging parking area. Energy transfer begins upon arrival.
Second-nearest station charging is full but has a free waiting slot. The vehicle is routed to the second-nearest station and directed to its dedicated waiting parking area (waiting_area). The vehicle's ID is appended to the end of the station's deque-based waiting queue. The vehicle enters the currently_waiting tracking dictionary and its waiting_start timestamp is recorded.
All candidate stations are completely full. Neither charging nor waiting slots are available at either candidate station. The vehicle is not rerouted and continues its original route. No charge_scheduled flag is set, allowing the system to retry the assignment at the next timestep.
Once a routing target is determined, the reroute_and_schedule_charge(vid, choice, batt) method is invoked. This method: (1) calls traci.simulation.findRoute to construct the complete edge sequence from the vehicle's current position to the station edge; (2) optionally appends a return route from the station back to the vehicle's original destination; (3) deduplicates consecutive identical edges in the resulting path; and (4) issues traci.vehicle.setRoute(vid, cleaned_edges) followed by traci.vehicle.setParkingAreaStop(vid, parking_area, duration=charge_time) to register the stop in SUMO's internal vehicle schedule. The calculated charge duration is derived from the energy needed to reach the 70% SOC target, the station's rated power, and its efficiency factor, clamped to the [30 s, 300 s] interval.
Arrival Detection and Physical Slot Assignment
The monitor_charging(t) method, called at every integer timestep, is responsible for detecting vehicle arrivals at stations and assigning them to the correct physical slot. For each active vehicle in the simulation, the method calls get_charging_station_id(vid), which inspects the vehicle's current stop list via traci.vehicle.getStops(vid) and cross-references the stoppingPlaceID attribute against the known charging and waiting area identifiers for all stations. A speed threshold of 0.5 m/s confirms that the vehicle has physically stopped at the location rather than merely passing through.
When a new arrival is detected at a station (i.e., the vehicle is neither in currently_charging nor in currently_waiting), the assign_vehicle_to_slot(vid, station_id, t) method is called. This method re-evaluates slot availability in real time—since conditions may have changed since the vehicle was initially routed—and assigns the vehicle to the appropriate physical area:
Charging slot available: The vehicle's ID is added to the station_charging_slots set, the currently_charging dictionary is updated, and the vehicle's charging_start timestamp and soc_start are recorded in vehicle_states.
Only waiting slot available: The vehicle's ID is appended to the station_waiting_queue deque, the currently_waiting dictionary is updated, the waiting_start timestamp is recorded, and a queue event is logged with the vehicle's queue position.
Station completely full: No assignment is made and a warning is issued. This case is rare under correct routing logic but is handled gracefully.

Charging Session Completion and State Cleanup
When a vehicle that was in currently_charging is no longer detected at a station (i.e., it has resumed driving after its scheduled stop duration expired), the handle_charging_complete(vid, t) method is triggered. This method retrieves the session's start timestamp and initial SOC from vehicle_states, queries the current battery level, computes the total charging duration and SOC gain, and appends a full charging event record to the charging_events list. The vehicle's ID is then removed from station_charging_slots and currently_charging, and all associated state keys are cleared from vehicle_states. An analogous cleanup is performed by handle_waiting_left(vid, t) for vehicles that depart from a waiting slot before being promoted, recording their total wait time in the queue_events log.
Vehicles that leave the simulation entirely (e.g., because they completed their route) are handled by cleanup_departed_vehicle(vid), which ensures they are removed from all tracking dictionaries—charging slots, waiting queues, and vehicle state maps—preventing stale data from inflating occupancy counts in subsequent timesteps.
Rule-Based Charging Recommendation System
In addition to the primary rerouting logic, the SmartChargingStationMonitor includes a secondary, advisory-layer recommendation engine implemented in the make_charging_recommendation(vehicle_id, timestep) method. This system is designed as a complementary analytical module: while the rerouting logic physically redirects vehicles in the simulation, the recommendation engine independently evaluates each vehicle and generates advisory records that are exported for post-simulation analysis and extension to future real-time advisory systems.
The recommendation engine activates for any vehicle whose SOC falls below 50% and at least 30 seconds have elapsed since its last recommendation (vehicle_last_recommendation cooldown), preventing recommendation flooding. For each eligible vehicle, the method calls find_nearest_and_second_nearest_stations(vehicle_id), which computes the Euclidean distance from the vehicle's current GPS coordinates (retrieved via traci.vehicle.getPosition) to the midpoint of each station's lane, ranks all stations by ascending distance, and returns the nearest and second-nearest stations with their full occupancy details.

Each recommendation record captures 22 fields, including vehicle identity and type, current edge, lane, speed, SOC, battery capacity, priority level, and full details for both the nearest and second-nearest stations (distance, power rating, charging and waiting slot availability, and occupancy rate). Records are buffered in the recommendations list and exported as a separate CSV file (charging_recommendations_{timestamp}.csv) upon simulation termination. CRITICAL and HIGH priority events also trigger immediate console output during runtime for real-time operator awareness.
Integrated Data Collection Orchestration
At every integer simulation second, the master collect_data(t) method orchestrates the full data collection pipeline in the following fixed sequence: (1) monitor_charging(t) is called first to update all slot assignments, detect arrivals and departures, and execute queue promotions; (2) the recommendation engine scans all active vehicles; (3) capture_station_snapshot(t) records a detailed per-station snapshot including charging and waiting vehicle counts, charging durations, power loads, and utilization percentages; and (4) collect_ml_features(t) generates one record per active vehicle per timestep (the ML dataset). System-level aggregate features—total active vehicles, total charging vehicles, system-wide average SOC, average speed, average charging duration, and total system load in kW—are computed by calculate_system_features(timestep_sec) and attached to every vehicle-level record as shared context columns, producing the final 34,020-record, 25-feature dataset exported as EV_Charging_Load_Demand_Dataset_{timestamp}.csv.
The total system load at any timestep is computed as the sum over all stations of the product of the number of actively charging vehicles at that station and the station's rated power: system_total_load_kW = Σ (vehicles_charging_at_station × station_power_kW). This deterministic calculation forms the target variable (system_total_load_kW) for all subsequent machine learning models, ensuring that the ground truth labels are physically grounded in the simulated charging events rather than estimated or inferred.
